# 第 J 組 SNA 網站報告｜四人、20 分鐘逐字稿

題目：**誰在開源專案裡連接程式碼與社群？**  
網站：[開源協作地圖](https://xxoon0987.github.io/sna-j-gharchive/)  
資料範圍：2025 年 1 月 UTC、十個 Hugging Face 儲存庫、GH Archive 公開事件。  
時間安排：四人各約五分鐘；以下時間包含網頁操作及短暫停頓。請用實際語速排練一次，讓總長控制在 19–20 分鐘。課程原定的五分鐘討論另計。

> 方括號是台上操作提示，不用念出來。講到「帳號」時不要自行改成「人」；一個 GitHub 帳號不一定等於一位可辨識的個人。

## 組員一｜0:00–5:00｜動機、問題與資料範圍

**畫面：首頁 →「研究問題」→「資料範圍」**

大家好，我們是第 J 組。今天要報告的題目是「誰在開源專案裡連接程式碼與社群？」我們把報告做成可以操作的網站，待會會直接切換不同類型的關係，讓大家看到同一批專案的網絡如何改變。

[停一秒，指向首頁標題。]

先想一個常見的開源協作情境：有人提出問題，有人在留言中釐清需求，有人提交程式碼修改，還有人審查這份修改。這些活動都在同一個專案裡發生，但參與者未必是同一批帳號。更進一步，有些帳號只出現在一個專案；有些則跨越好幾個專案，讓原本分開的參與群產生連結。社群網絡分析可以幫助我們描述這種「誰和哪些專案有關係」的結構。

為什麼這值得研究？如果只看程式碼提交，我們容易忽略提出問題、回應使用者和審查修改的人；如果只看討論，也可能看不到程式碼如何被整合。因此，我們不先假設「貢獻者」只有一種樣子，而是把可觀察的活動分開，再比較它們之間的連結。這也是本報告使用社群網絡分析，而不只列出各專案事件總量的原因。

[點「研究問題」。]

我們有三個問題。第一，參與 issue、PR 和 review 的帳號是否重疊？第二，哪些帳號跨越多個專案？第三，當我們改用不同事件定義關係時，網絡圖會不會改變？這裡的「橋接」先是網絡位置的描述，不代表某個人比較重要，也不代表我們知道他在私下做了哪些協調工作。

這三個問題各自需要不同的讀法。角色重疊要比較帳號集合；跨專案參與要看帳號連到幾個儲存庫；網絡變化則要固定同一批專案和同一段時間，只改變事件類型。這樣一來，圖變了，我們至少知道是哪一個分析定義改變，而不會把時間和選樣的差異也混進來。

[點「資料範圍」。]

資料來自 GH Archive 收錄的公開 GitHub 事件，我們透過 ClickHouse 的公開 GitHub Events 資料鏡像查詢。時間固定為 2025 年 1 月 1 日零時，到 2 月 1 日零時之前，全部採 UTC。固定一個月，是為了讓不同事件類型能在同一個時間視窗比較。

研究對象是 Hugging Face 組織的十個 GitHub 儲存庫，包括 Transformers、Datasets、Tokenizers、Accelerate、Diffusers、PEFT、TRL、Hugging Face Hub、Smolagents，以及 Text Generation Inference。這裡「Datasets」是其中一個程式碼專案的名稱；這十個是程式碼儲存庫，不是十份資料集，也不是某個人的私人 GitHub。不同帳號可以提出 issue、留言、提交 PR；有寫入權限的維護者才可直接修改或合併主專案的程式碼。我們觀察的是公開事件，不能說所有參與者都共同編輯了同一份程式碼。

選同一生態系，是因為它們有共同的技術脈絡，較適合觀察跨專案參與。這是有目的的個案選擇，不是隨機抽取 GitHub 專案，所以稍後的結論只適用於這十個專案和這一個月。

大家可以在畫面上看到十個專案名稱。它們不是完全一樣的產品：有模型工具、資料工具、應用與推論相關的儲存庫。對我們來說，重要的不是把它們當成整個開源世界的縮影，而是設一個可清楚說明的邊界，然後問：在這個邊界裡，誰的公開活動跨過了專案？

原始查詢取得 13,555 筆所選事件。每筆至少有發生時間、帳號、儲存庫及事件類型；我們只擷取分析需要的欄位，沒有逐小時下載 GH Archive 原檔。接著做資料清理：排除帳號名稱以「[bot]」結尾的 405 筆，以及可辨識的文件建置帳號 408 筆，共 813 筆。留下 12,742 筆分析事件，涉及 1,379 個帳號。其中 93 個帳號在選定期間參與至少兩個專案。排除可辨識機器人不代表保證排除了全部自動化活動。

接下來請第二位組員說明我們如何把事件變成網絡，並現場操作這張圖。

## 組員二｜5:00–10:00｜事件定義與互動網絡

**畫面：「資料範圍」四層事件 →「互動網絡」；依序點「全部」、「Issue」、「討論」**

先解釋三個詞。Issue 像公開的「問題單」：有人回報錯誤、提出功能需求或待辦事項；提出 issue 不等於改了程式。PR 是 pull request，像把自己做好的修改送出來請專案合併；提出 PR 也不保證已被接受。Review 是別人針對 PR 做審查，例如提出修改建議或核准；審查者與 PR 作者可以是不同帳號。

我們把公開事件整理成四層。第一層是 Issue，對應 GitHub 的 IssuesEvent，這個月有 1,070 筆。第二層叫「討論」，對應 IssueCommentEvent，共 4,474 筆。要特別注意，GitHub 的 IssueCommentEvent 既可能是 issue 下的留言，也可能是 PR 下的留言，所以我們沒有把它說成純粹的 issue 討論。第三層是 PR，也就是 PullRequestEvent，共 1,874 筆。第四層是 Review，合併 PR 審查與審查留言事件，共 5,324 筆。這四層是不同的觀察角度，不是四種互斥的「人」。資料裡的帳號是事件觸發者；例如關閉 PR 的維護者不一定是原作者，因此 PR 帳號不等於 PR 作者名單。只是點開 PR 閱讀，也不算本研究的審查事件。

[點「互動網絡」，停兩秒讓圖顯示。]

這張圖是「帳號與儲存庫」的二模網絡。左邊十個點是專案，右邊的點是 GitHub 帳號。只要帳號在某專案留下至少一筆目前選定類型的公開事件，我們就畫一條線。例如提出 issue 會在 Issue 層連線；提交 PR 會在 PR 層連線；留下審查則會在 Review 層連線。只留言也可能在討論層連線，所以這條線不一定代表修改程式碼，更不代表修改被合併。線表示「有符合定義的參與」，不會因為事件多就畫得更粗。

在數學上，我們把帳號放成矩陣的列、儲存庫放成欄；有符合條件事件填 1，沒有填 0。帳號那一列的 1 加起來，就是它連到的專案數，稱為 degree。這與課程第 2 週 Davis Southern Club Women 的「女性乘社交活動」出席矩陣是同一種雙模資料結構；我們分析的不是那份歷史資料，而是把相同方法用在 GitHub 事件。共同參與一個專案，也不等於兩個帳號直接認識。

這裡要分清楚：線不是「兩位開發者彼此認識」，也不是「某個專案引用另一個專案」。它只連接帳號和事件發生的儲存庫。如果兩個專案連到同一個帳號，我們可以說兩個專案有共同的可觀察參與者；但不能只靠這條路徑，說兩個專案的團隊曾直接合作。這是二模網絡和一般人際關係圖最重要的差別。

[保持「全部」。指向圖上方統計。]

在「全部」模式，上方顯示的是 12,742 筆事件、1,379 個帳號，以及 93 個跨專案帳號。圖右側只顯示最多 40 個示例帳號，為了讓線條可以閱讀；上方統計涵蓋該類事件的所有保留帳號；四種中心度則固定在全部事件的 93 個跨專案帳號加 10 個儲存庫核心上計算。示例帳號依所選事件層核心中的中介中心度挑選。簡單說，中介中心度描述一個節點在其他節點之間的最短路徑上出現的程度，這是一個結構指標，不是能力評分。

[點圖左側 Transformers 的圓點，再點右側 Wauplin 的圓點。]

點選專案時，右側會列出這個專案的參與帳號數、四類事件組成，以及共同參與者較多的其他專案。點選帳號時，會看到它在本圖參與哪些專案。例如「全部」圖中的 Wauplin 連到五個選定專案。這說明它在我們定義的觀察範圍裡跨越多個儲存庫；單看這張圖，不能說它促成了哪些具體決策。

右側細節同時保留事件次數，讓我們看到活動量和網絡位置是否一致。它們可能不同：一個帳號可以在單一專案非常活躍，卻沒有跨庫連結；另一個帳號可能事件不多，但剛好參與幾個不同專案。因此，今天我們不會用事件數直接取代橋接指標，也不會用橋接指標評判個人。

[點「Issue」。]

現在只保留 Issue 事件，畫面變成 1,070 筆事件、538 個帳號，其中 23 個跨越至少兩個專案。請看線條變少、圖中的帳號也改變了。這表示若只用 issue 動作來定義參與，我們看到的網絡和剛才的「全部」不同。

[點「討論」。]

切到討論層後，是 4,474 筆事件、1,035 個帳號，跨專案帳號有 62 個。差異反映的是「我們量測哪一種行為」，不能直接推成有人離開社群，或某一類活動一定更有價值。第三位組員接著會比較 PR 與審查層，並回答不同角色到底重疊多少。

這兩個切換也提醒我們，研究結果會受「邊的定義」影響。同一個帳號可能在討論層連到某個專案，在 Issue 層卻沒有連線，因為它留下的是留言，不是 IssuesEvent。這種缺席只表示沒有符合當前定義的事件，不表示這個帳號完全沒有關心該專案。

## 組員三｜10:00–15:00｜角色切換與主要發現

**畫面：「互動網絡」點「PR」、「Review」→「研究發現」**

[點「PR」。]

剛才是議題和討論；現在看程式碼相關的活動。PR 層有 1,874 筆事件，涉及 388 個帳號，其中 27 個帳號跨越兩個以上選定專案。請注意，圖上連線變化很大：這不是網站重新排版而已，而是關係定義從「曾有 issue 或留言動作」換成「曾有 PR 動作」。

[點「Review」。]

Review 層有 5,324 筆事件，但涉及的帳號是 175 個，跨專案帳號是 27 個。這層包括 PR 審查事件和審查留言，因此事件筆數不能直接當成「審查了幾份 PR」。它說明的是，在所選事件定義下，審查相關活動集中在比 PR 動作更小的帳號集合。不同事件會產生不同大小的帳號群，這也影響接下來的重疊比較。

這裡可看到一個有意思的對比：Review 的事件筆數比 PR 多，但有 Review 事件的帳號卻比有 PR 事件的帳號少。我們只能說，在所選事件資料裡，兩層的事件數和參與帳號數分布不同；不能把不同事件的筆數當作等量的工作單位。一次審查、一則審查留言和一次 PR 動作，本身就不是相同的行為。

[點「研究發現」，指向三條 Jaccard 橫條。]

第一個研究問題是：這些角色是否由同一批帳號扮演？我們用 Jaccard 相似度比較帳號集合。算法是「兩組共有多少帳號」，除以「至少屬於其中一組的帳號有多少」。例如兩組共有 10 個帳號、合起來有 50 個不同帳號，Jaccard 就是 0.2。它不是把共有帳號除以其中一組，所以不能把 0.2 說成「某一組有 20% 的人轉去做另一件事」。

用實際資料示範：Issue 和 PR 共同出現的帳號是 125 個；至少參與其中一種的不同帳號共有 801 個。因此 Jaccard 是 125 除以 801，四捨五入為 0.156。Issue 與 Review 是 0.107；PR 與 Review 是 0.291。三組比較裡，PR 與 Review 的帳號集合相對比較接近；Issue 與 Review 的重疊較少。不過，0.291 仍遠低於 1，不能說提交 PR 和參與審查的是完全同一批帳號。

如果把它們換成比較好理解的說法，0.156 代表 Issue 與 PR 兩組的「聯集」中，大約 15.6% 的帳號同時在兩組；0.107 代表 Issue 與 Review 的聯集裡，大約 10.7% 同時在兩組。這不是每個帳號固定的角色標籤，也沒有追蹤某個人先提 issue、後送 PR 的時間順序。我們只是在同一個月內比較他們是否留下相應事件。

[指向「59」的卡片。]

如果換一個角度，把 issue 或討論視為「社群活動」，把 PR 或 review 視為「程式碼活動」，同時在兩側都有事件、又參與至少兩個專案的帳號有 59 個。這是我們能從公開事件辨認的「跨角色、跨專案」參與者。但「有兩種活動」不等於真的協調了兩個團隊；要回答影響力，還需要訪談或更細的內容分析。

也請注意，「59」的門檻比前面的「93」更嚴格。93 只需要參與至少兩個選定專案；59 除了跨專案，還必須在社群類和程式碼類事件中都出現。所以這兩個數字回答的是不同問題。這樣逐步增加條件，比直接稱某些帳號為「核心人物」更容易讓別人檢查我們的結論。

所以目前的答案是：角色之間確實有交集，但並不完全重合。第四位組員會用中心度比較跨專案帳號的網絡位置，再說明研究限制。

## 組員四｜15:00–20:00｜中心度、限制與結論

**畫面：「研究發現」四張中心度卡、時間切片與審查卡片 →「方法與限制」**

[捲到四張中心度卡，指出各卡的排名。]

接著看老師第 6 週教的中心度。為了讓四種指標可比，我們固定「全部事件」的同一張核心圖：93 個跨庫帳號、10 個儲存庫、229 條無方向、無權重的連線。Degree 是直接連到幾個專案；closeness 是到其他節點的最短路徑較短；betweenness 是位在其他節點最短路徑中間的程度；eigenvector，也就是特徵向量中心度，則讓連到結構上較中心專案的帳號得到較高分。最後一個可以寫成 A x 等於 λ x。這四把尺回答不同問題，不能混成單一「最有貢獻的人」排行榜。

例如 degree 最高分是連五個選定專案；中介中心度前面有 Wauplin，而 eigenvector 的最高帳號包含 faaany。排名不同，表示「連得多」、「在路徑中間」與「連到中心節點」並不完全相同。分數只對這張界定好的網絡成立，不能推成現實中的權力或能力。

[向下捲到一月四段時間切片。]

這裡把一月分成四段。前三段各七天，最後一段有十天；為了避免十天那段只因時間較長就看起來最多，我們先除以天數，再比較每日平均。四段全部所選事件的每日平均大約是 291、443、436、455 筆。這顯示在這個月份裡，第一段的公開活動較少，後面三段相近；但只有一個月、四個切片，不能據此判定長期趨勢，也不能直接推定是什麼事件造成差異。

在這張條形圖中，顏色也對應前面四類事件。大家可以看到，不只是總量，事件組成也可以分開觀察。若將來要研究某次產品發布是否改變協作方式，就需要更長的前後期間、明確的發布日期，以及相同的專案和事件定義；今天這個圖只做描述，不做那樣的因果檢驗。

[指向「可辨識方向的審查事件」卡片。]

前面的主圖只問帳號有沒有參與某個專案，並沒有畫出人和人的方向。這裡我們另外做一個較窄的有向關係：只取 PullRequestReviewEvent，如果資料可以辨識審查者與 PR 作者，就建立「審查者指向 PR 作者」的邊，並排除自己對自己的關係。結果有 2,058 筆這樣的審查事件、675 種審查者與作者配對。這裡沒有把一般留言推成「留言者指向原作者」，因為所用資料欄位不足以可靠建立那條人際邊。

同一組審查者與作者在一個月內可能對應不只一筆事件，所以 2,058 是事件數，675 是不同的帳號配對數，兩者不能互換。這個方向是由事件結構定義出來的，不表示審查者一定指導作者，也不表示作者必然受審查者影響。我們把關係縮窄到能可靠辨識的欄位，避免畫出沒有資料支持的箭頭。

[點「方法與限制」，停兩秒。]

最後說明我們可以回答到哪裡。第一，GH Archive 記錄的是 GitHub 上的公開事件；私下討論、線下工作和未被選進的事件，都不在這張圖中。第二，十個專案是目的性選樣，期間只有 2025 年 1 月，不能把結果說成整個 GitHub 的規律。第三，我們排除了可辨識的機器人帳號，但可能還有沒辨識到的自動化活動。第四，四種中心度只描述這個界定網絡的不同位置；事件數和中心度都不是對個人貢獻的評分。

為了讓結論可檢查，網站提供來源、查詢 SQL、處理程式和重現步驟。別人可以改用更長的期間，或比較另一個開源生態系，但要保留清楚一致的節點、事件和關係定義，結果才有可比性。

如果老師或同學對某個數字有疑問，我們可以回到方法頁，確認日期起訖、資料欄位、機器人如何排除，以及四種中心度在哪個網絡上計算。網站還提供 93 個跨庫帳號的完整中心度 CSV，可核對排名。這也是把成果做成網站的另一個好處：報告時可以互動探索，報告後也能從同一個頁面追溯資料與分析規則。

回到最初的問題：在這十個 Hugging Face 專案、2025 年 1 月的公開事件中，issue、PR 與 review 的帳號集合只有部分重疊；93 個帳號跨越至少兩個專案，其中 59 個同時有社群和程式碼相關活動。切換事件類型時，網絡也跟著改變。這讓我們看到，開源協作既有不同分工，也有跨越分工與專案的參與者。以上是第 J 組的報告，謝謝大家，歡迎提問。

## 上台前一分鐘檢查

1. 用正式網址登入並確認 `data.json` 已載入；不要依賴 `127.0.0.1` 本機預覽網址。
2. 先把瀏覽器縮放設成 100%，必要時按網站右上角「簡報模式」。
3. 組員二練習點選 Transformers 與 Wauplin；組員二、三確認四個篩選按鈕都能切換。
4. 每位組員排練約五分鐘；若超時，先縮短操作停頓，不要刪掉方法限制。
