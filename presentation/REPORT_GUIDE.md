## 一句話結論

在選定的十個專案與一個月內，issue、PR、review 的參與帳號只有部分重疊；跨專案活動由少數帳號串起，但事件數量與網絡橋接位置不能直接等同貢獻價值。

## 示範時要說的數字

- 原始查詢 13,555 筆；排除已辨識的自動化帳號 813 筆後，保留 12,742 筆。
- 1,379 個分析帳號；其中 93 個參與至少兩個選定專案。
- 四層事件：Issue 1,070、討論 4,474、PR 1,874、Review 5,324。
- 角色重疊低不代表角色互不相干：單次發問的帳號很多，而審查帳號群較小。比較要同時交代集合大小。
- 本組的數學與課本對照：0／1 雙模矩陣（W02 Davis Women×Events）、Jaccard `125/801=0.156`、四種中心度（W06 第 10 章）。特徵向量 `A x = λ x` 在這裡只描述連到結構上較中心的專案。

## 5 分鐘討論預備

**Q：為什麼只挑 Hugging Face？**  同一生態系較容易界定專案邊界，也較可能看出跨庫參與；這是目的性個案，不能外推至所有開源專案。

**Q：事件多的人就是橋接者嗎？**  不一定。事件數是活動頻率；二模中介中心度看帳號連接的路徑位置。網站同時列出兩者，但都不等於能力評分。

**Q：IssueCommentEvent 能代表 issue 討論嗎？**  它也包含 PR 留言，所以獨立成「討論」層。網站未把它當成純 issue 層，也沒有據此建留言者與原作者的人際邊。

**Q：資料裡還有機器人嗎？**  排除了 `[bot]` 結尾帳號與可辨識的 DocBuilder 自動化帳號，但可能仍有未辨識的自動化活動。這是研究限制。

**Q：怎麼重做？**  網站「方法與限制」有查詢 SQL、程式與步驟；原始事件列不在網站上，執行腳本可重新取得。

## 講述邊界

說「在這十個專案、這個月份、這些公開事件裡觀察到」，避免將結果說成整個 GitHub 的規律。展示公開帳號時談事件與位置，不評論個人能力。
