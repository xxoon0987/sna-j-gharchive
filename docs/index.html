01 / THE QUESTION

「有參與」與「能橋接」
是兩件不同的事。

我們把事件拆成不同角色，觀察同一批帳號是否同時出現在議題、PR 與審查網絡，以及誰跨越不同儲存庫。

Q / 01
◇

角色是否重疊？

參與 issue 動作、PR 動作與 review 的帳號，有多少是同一批人？

↔

在十個專案中，哪些帳號連接原本分開的參與群？

◎

不同網絡怎麼變？

切換事件類型後，專案間的共同參與者與橋接路徑是否改變？

02 / DATA BOUNDARY

把觀察邊界
說清楚。

資料取自 GH Archive 公開 GitHub 事件，透過 ClickHouse 的公開鏡像查詢。以 2025 年 1 月為固定視窗，選取同一開源生態系中的十個專案，便於觀察跨庫參與。

PROJECT SET10 REPOSITORIES
EVENT LAYERS4 LENSES

Issue：提出、關閉或重新開啟議題；不等於修改程式碼。

討論：在 issue 或 PR 下留言，兩者在此資料中不硬拆。

PR：提出、關閉或重新開啟程式碼修改提案；提出不等於已合併。

Review：送出 PR 審查或留下審查意見；只是點開閱讀不算。

帳號記錄事件的觸發者，例如關閉 PR 的帳號可能是維護者，未必是 PR 作者。

這十個是 GitHub 程式碼儲存庫，不是十份資料集。它們位於 Hugging Face 組織帳號下；公開專案可由外部帳號提議修改，是否合併由專案維護者決定。我們查詢事件的時間、帳號、專案、類型及少量分析欄位，不下載留言全文。13,555 筆查詢結果中排除 813 筆可辨識的自動化帳號事件，這一步屬於資料清理。

04 / WHAT THE DATA SAYS

角色有交集，
但並不完全重合。

以下數字比較的是帳號集合，不是工作品質。Jaccard 相似度＝兩組共同帳號 ÷ 兩組至少參與一種事件的帳號；越接近 1，重疊越多。

ROLE OVERLAP / JACCARD

Issue 指 IssuesEvent；PR 指 PullRequestEvent；Review 指 PR 審查與審查留言。它們是不同大小的帳號群，解讀時需同時看樣本量。

CROSS-ROLE BRIDGES —

個帳號兼具社群與程式碼活動，且參與兩個以上專案。

這些帳號在 issue／討論與 PR／審查至少各留下事件。這表示可觀察的跨角色參與，不能單憑事件推定其實際影響力。

TIME SLICES / EVENTS PER DAY

一月四段時間切片

末段包含 10 天，其餘每段 7 天，因此將各類事件換算成每日平均後比較。

W06 / CENTRALITY LAB

用哪一把尺，找出「重要」的網絡位置？

為了公平比較，四項指標都在同一張「全部事件」二模核心上計算：— 個跨專案帳號、— 個儲存庫、— 條二元連線。關係無方向、無權重；只要有至少一筆事件就連線。分數描述位置，不是人物能力排名。

BASIC MATH / 關係矩陣

帳號在專案有至少一筆所選事件，矩陣格子記 1；沒有則記 0。帳號的 degree ＝該列的 1 相加。

BASIC MATH / 角色重疊

Issue 與 PR 共有 — 個帳號、合計有 — 個不同帳號；Jaccard ＝共有 ÷ 合計 ＝ —。

03 / 橋接

看跨庫路徑

至少參與兩個專案的帳號進入二模核心，以標準化中介中心度描述其所在位置。

04 / 倫理

謹慎解讀

平台事件不是完整工作紀錄；中心度不是能力或貢獻價值排名，也不能推論因果。

COURSE CONNECTION / 課本對照

和課堂的雙模網絡是同一種資料結構。

第 2 週 Davis Southern Club Women 用「女性 × 社交活動」的 0／1 出席矩陣；本組改成「GitHub 帳號 × 儲存庫」的 0／1 事件參與矩陣。兩者都能比較共同參與，但共同出現不等於友誼或實際合作。第 6 週教的 degree、closeness、betweenness、eigenvector，則用來比較同一張網絡的不同位置。
