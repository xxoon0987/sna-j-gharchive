01｜先看懂這個報告

我們到底在研究什麼？

開源軟體的工作可能由不同帳號完成：有人發現問題、有人回答、有人的修改被送出審查。這份報告把公開活動紀錄整理成關係圖，觀察「哪些帳號參與哪些專案」，以及不同活動的參與帳號有多少重疊。

例如甲帳號只在專案 X 留言，乙帳號同時在 X 和 Y 有活動。兩者都有參與，但乙在這個觀察範圍內具有跨專案位置。這個位置值得研究，卻不能單靠它斷言乙比較厲害，或真的促成兩個團隊合作。

三個研究問題

問題 使用的資料或方法 可以回答的事情
Issue、PR、Review 是不是同一批帳號？ 比較帳號集合，計算 Jaccard 兩種活動的參與帳號重疊程度
哪些帳號跨越專案？ 帳號連到的不同儲存庫數與四種中心度 帳號在界定網絡內的位置
換一種活動，網絡會怎麼變？ 固定時間與十個專案，切換事件類型 關係定義改變後，帳號數與連線如何改變

可以用這句話介紹報告

我們用 2025 年 1 月十個 Hugging Face 專案的公開 GitHub 事件，研究不同活動的帳號是否重疊，以及哪些帳號跨越專案。我們把事件轉成帳號與儲存庫的網絡，用 Jaccard 和四種中心度描述參與模式。

我們做了哪些分析工作？

  1. 設定研究範圍：十個儲存庫、一個月、五種事件。
  2. 從 ClickHouse 的 GH Archive 鏡像查詢需要的欄位。
  3. 排除可辨識的自動化帳號事件。
  4. 把事件整理成帳號集合與 0／1 參與矩陣。
  5. 計算重疊、跨專案參與、四種中心度與每日平均。
  6. 把結果做成能切換事件類型的網站，附上程式和解讀限制。

這是「既有資料的再分析」。資料的收集來源與本組的分析貢獻應分別交代。

下一篇：資料來源、欄位與清理

02｜資料來源、欄位與清理

資料從哪裡來？

GH Archive封存 GitHub Events API 的公開活動紀錄，官方按小時提供壓縮的 JSON 事件檔。本組使用 ClickHouse 的公開 github.github_events 鏡像查詢需要的範圍，回傳格式是 JSONEachRow，儲存成 .jsonl 檔：每一行是一筆事件物件。

ClickHouse 的公開匯入程式顯示它從 GH Archive 的逐時檔取得資料並整理欄位。本組沒有自行下載全部逐時壓縮檔，也沒有逐筆比對鏡像與官方原檔，因此不能宣稱兩者完全一致或完整無遺漏。

採用鏡像本身不必然比較不精確；要確認完整性，需要檢查期間、篩選、欄位轉換、回傳限制與原始紀錄。下載更多不相關資料，也不會自動改善本研究的精確性。

這份資料涵蓋什麼？

條件 本組的設定
開始時間 2025-01-01 00:00:00 UTC，包含這個時間
結束時間 2025-02-01 00:00:00 UTC，不包含這個時間
專案 前一篇列出的十個 Hugging Face 儲存庫，以固定 repo ID 查詢
事件 IssuesEvent、IssueCommentEvent、PullRequestEvent、PullRequestReviewEvent、PullRequestReviewCommentEvent
沒有納入 PushEvent、星號、fork 等其他事件；私人與線下活動
查詢方式 分成 1–7、8–14、15–21、22–31 日四段

這是 UTC 的一月，與台灣時間零時起訖的一月不同。日期屬於 2025 年；報告網站整理於 2026 年。

原始資料不是三個勾選欄位

原始資料是一筆筆活動。以下為虛構教學例子，不是研究中的原始列：

時間 觸發事件的帳號 儲存庫 事件類型 動作
1 月 3 日 A 專案 X IssuesEvent opened
1 月 5 日 A 專案 X PullRequestEvent opened
1 月 8 日 B 專案 Y PullRequestReviewEvent created
1 月 9 日 A 專案 Y IssueCommentEvent created

同一個帳號可能出現很多次。分析時，才把它轉成「這個帳號是否有 Issue 活動」「是否參與某個專案」等 0／1 欄位。1 表示至少有一筆符合條件紀錄；0 表示這份選定資料中沒有這種紀錄。

資料沒有擷取留言正文、完整修改內容、GitHub event ID、actor ID 或是否合併等欄位。因此無法用這份擷取資料直接判斷每筆 PR 最後是否成功、內容品質、真人身分或完整事件去重。帳號名稱改變也沒有另外做身分合併。

Issue、PR、Review 到底是什麼？

類別 白話情境 本組計入的活動 不能直接當成什麼
Issue（議題） 「這裡有錯誤」「希望增加功能」等問題單 IssuesEvent；本快照有開啟、關閉、重新開啟 已解決問題、已修改程式碼
討論 在 issue 或 PR 下留言 IssueCommentEvent 全部都是 issue 留言，或留言一定回給原作者
PR（Pull Request） 已準備一份修改，請專案考慮合併 PullRequestEvent；本快照有開啟、關閉、重新開啟 只有口頭建議、已成功合併，或每位事件觸發者都是 PR 作者
Review（審查） 對 PR 提交審查或留下程式碼審查留言 PullRequestReviewEvent 加 PullRequestReviewCommentEvent 只點開瀏覽、一次事件就等於一份完整審查

PR 可以包含文件、設定與程式碼等修改。GitHub 的帳號角色不是固定職業：同一帳號可以同時出現在多個類別。GitHub 官方事件定義可用來核對事件觸發者與 payload。

下一篇：從事件到網絡與數學

03｜從事件到網絡與數學

第一步：決定一條線代表什麼

一條線代表：某帳號在某儲存庫、選定期間內，至少有一筆符合目前事件類型的紀錄。它可以來自議題、留言、PR 或審查。這不要求程式碼真的被修改或合併。

先用虛構例子看 0／1 矩陣：

帳號 專案 X 專案 Y 專案 Z 一列加總
A 1 1 0 2
B 0 1 0 1
C 1 0 1 2

A 在 X 有十筆、Y 有一筆事件，也只連到兩個不同專案，因此 degree 是 2。B 只連到 Y。矩陣的 0 僅代表「沒有觀察到符合定義的事件」，不代表帳號完全沒有關心或私下參與該專案。

記這張矩陣為 B，則 B[a,r] = 1 表示帳號 a 參與儲存庫 r。帳號 degree 是 Σ_r B[a,r]；兩個專案的共同參與帳號數是 Σ_a B[a,r1] × B[a,r2]。例如 X 和 Y 共同連到 A，故共同帳號數為 1。

這是「二模／雙模網絡」：節點有帳號、儲存庫兩種，邊連在不同種類之間。主圖沒有直接畫「帳號與帳號互相認識」或「專案依賴另一專案」。

第二步：1,379、93、59 分別怎麼來？

  1. 對清理後事件的 actor_login 取不同值，得到 1,379 個帳號名稱。
  2. 對每個帳號計算出現過的不同儲存庫數；數量至少 2 的有 93 個。
  3. 在這 93 個中，再要求帳號至少有一次「Issue 或討論」，以及至少有一次「PR 或 Review」，得到 59 個。

這裡把 Issue／討論稱為「社群類」、PR／Review 稱為「程式碼類」，只是本報告的分析分類。PR 也可能改文件，Review 也包含溝通，不代表兩類活動在現實中完全分離。

虛構帳號 活動 跨至少兩個專案？ 同時有兩類活動？ 算入 93？ 算入 59？
A 在 X 提 Issue，在 Y 做 Review 是 是 是 是
B 在 X、Y 都提 Issue 是 否 是 否
C 只在 X 提 Issue 和 PR 否 是 否 否
D 只在 X 做 Review 否 否 否 否

不要求在每個參與專案都做過兩類活動，也不要求 Issue 和 PR 對應同一個問題。這項條件沒有檢查行為先後。

完整 1,379 個帳號中，同時有兩類活動的共有 312 個；其中 59 個還跨至少兩個專案。這也說明「跨角色」和「跨專案」是兩個不同條件。

第三步：Jaccard 衡量兩組帳號的重疊比例

把有 Issue 事件的帳號集合叫 I，把有 PR 事件的帳號集合叫 P：

Jaccard(I,P) = |I ∩ P| / |I ∪ P|
交集 I ∩ P：兩種事件都有的不同帳號
聯集 I ∪ P：至少有其中一種事件的不同帳號

本組的實際數值：

Issue 帳號：538
PR 帳號：388
共同帳號：125
聯集：538 + 388 − 125 = 801
Jaccard：125 ÷ 801 = 0.156054… → 網站顯示 0.156

0 代表沒有共同帳號，1 代表兩組帳號完全相同。這不是「連擊次數」，也不看帳號先做哪件事。0.156 的分母是聯集 801，不是 Issue 的 538 或 PR 的 388；因此不能說成「15.6% 的 Issue 帳號轉去寫 PR」，更不能說「15.6% 的議題被解決」。

第四步：固定同一張圖，計算四種中心度

中心度要先說明「對哪張網絡計算」。本組四項比較固定使用全部所選事件的跨專案二模核心：

設定 值與意義
帳號門檻 在十個專案中至少參與 2 個
帳號節點 93
儲存庫節點 10
總節點數 n 103
邊數 229
方向 無向；一條帳號—專案參與關係
權重 無權重、二元；活動次數不加重邊
連通性 核心為連通圖，所有節點之間存在路徑
計算對象 路徑可經過全部 103 個節點，呈現排名只比較 93 個帳號

完整帳號—專案矩陣是 1,379 × 10，共 1,515 條不同的參與關係；扣掉 1,286 個單一專案帳號後，核心矩陣是 93 × 10，共 229 條關係。這裡的「核心」只是我們的取樣名稱，不是 k-core 演算法。

Degree：直接連到幾個專案？

白話是「參與範圍有多廣」。公式為 degree(a) = Σ_r B[a,r]。這裡展示原始連結數，不是除以 n−1 的標準化 degree centrality。Wauplin 在核心連到 5 個選定專案，所以 degree＝5。事件發生一百次也不會把同一條邊算一百次。

Closeness：沿著關係，到其他節點的距離有多短？

白話是「從這個位置出發，沿網絡走到其他位置是否比較近」。在本組連通核心中，C(a) = (n−1) / Σ_{v≠a} d(a,v)，其中 d 是最短路徑的邊數，n＝103。使用 networkx.closeness_centrality(core)。

帳號到專案可能一步，帳號到另一帳號至少兩步，路徑會在兩種節點之間交替。這是數學距離，不是訊息實際傳遞速度，也不是兩個人感情的親近程度。

Betweenness：有多少最短路徑經過這裡？

白話是「這個節點多常位在別的節點之間的最短路徑上」。對不包含 a 的節點對 s、t，加總 σ_st(a) / σ_st：σ_st 是兩者最短路徑總數，σ_st(a) 是其中經過 a 的數量。若有多條同長度路徑，會按比例分配。

本組使用 networkx.betweenness_centrality(core, normalized=True)，無向圖標準化係數為 2 / ((n−1)(n−2))。未抽樣近似，邊不加權，路徑端點不計入。這是一般圖的標準化公式，沒有改用雙模專屬的標準化方式。

分數較高可用來描述橋接位置，但我們沒有觀察資訊真的沿最短路徑傳遞，也沒有因此證明該帳號促成合作。

Eigenvector：連到的節點是否也處於中心？

白話是「連結的數量以外，也考慮所連節點在整張圖裡的位置」。在這張二模圖，帳號連到儲存庫；儲存庫又連到帳號，分數由彼此的連結結構共同決定。不能簡化成「認識名人」或「專案星號多」。本計算沒有輸入星號、粉絲或職稱。

數學上，把核心參與矩陣 B 轉成 103 × 103 的對稱鄰接矩陣 A：

A = [ 0    B  ]
    [ Bᵀ   0  ]
A x = λ x

x 是每個節點的分數，λ 是對應的特徵值；等價地，一個節點相鄰節點的分數總和，等於自身分數乘上 λ。計算使用 networkx.eigenvector_centrality(core, max_iter=1000, tol=1e-10)，預設等值初始向量與 weight=None。NetworkX 在冪次迭代中使用 A＋I 幫助收斂，特徵向量方向不變。演算法說明

計算後將帳號分數除以最高帳號分數，讓最高值為 1。1 不是 100% 影響力；0.8 也不是 80% 的貢獻。它是這張網絡內的相對分數。改動時間、專案、核心門檻或事件定義，結果可能改變。

四種指標回答不同問題，因此不加總成一個「最重要人物」總分。公開 CSV 保留五位小數，網站卡片顯示三位；顯示同分不一定代表未四捨五入前完全相同。

圖上為什麼沒有畫出全部帳號？

  1. 整體統計涵蓋所選類型的所有保留帳號。
  2. 各事件層先找出跨至少兩個專案的帳號，建立該層核心。
  3. 為了可讀性，圖上最多畫 40 個帳號，按該層未四捨五入的中介中心度挑選。同分再比較專案數、事件數與帳號名稱。

所以，沒有出現在示例圖上不代表沒有參與。切換 Issue／PR／Review 後，門檻套用的是該類事件，示例帳號也可能改變。下方四張中心度比較卡始終使用「全部事件」核心，不跟著篩選器重新計算；分層核心可能不連通，不能直接把不同層的分數當成同一尺度比較。

每日平均與有向審查網絡

時間切片前三段各 7 天，最後一段 10 天。用 該段事件列數 ÷ 天數 算每日平均，才不會只因天數更多就看起來比較活躍。

有向審查分析是另一個補充分析：只取 PullRequestReviewEvent，以事件觸發帳號為審查者、該類事件中的 creator_user_login 為 PR 作者，建立「審查者 → PR 作者」。排除作者缺漏、作者被辨識為自動化帳號及自己指向自己的情況。沒有用留言事件推斷留言者的對話對象。四種中心度使用前述帳號—儲存庫無向核心，並非這個有向人際網絡。

與課文怎麼對照？

課程 W02的 Davis Southern Club Women 是「女性 × 社交活動」的 0／1 出席矩陣；本組是「帳號 × 儲存庫」的 0／1 事件參與矩陣。兩者資料結構相似，使用的資料集不同。共同出席不等於友誼，正如共同參與專案不等於帳號曾直接合作。

課程 W06列出 degree、closeness、betweenness、eigenvector，對應 Hanneman & Riddle 第 10 章的中心度主題。本組比較同一張圖的四種位置，並公開參數。跨專案與中介位置也可連結「橋接」概念，但本組未計算 Burt constraint 或 effective size，不能宣稱已完成正式的結構洞指標分析。

如何讀 93 與 59？

  • 93 是「在至少兩個選定專案留下任一所選事件」的帳號。
  • 59 是其中又同時有「Issue／討論」和「PR／Review」活動的帳號。
  • 93 / 1,379 ≈ 6.7% 是保留帳號中跨專案的比例。
  • 59 / 93 ≈ 63.4% 是跨專案帳號中又跨兩類活動的比例；59 / 1,379 ≈ 4.3% 是全體保留帳號中的比例。報告比例時必須說明分母。

「跨角色」只是可觀察的活動組合，不代表已確認帳號的職務、專業身分或協調成果。

四種中心度顯示不同的位置

指標 排名前列的例子 可以怎麼說

Closeness stevhliu、Wauplin 均約 0.48571 在這張核心中，到其他節點的最短路徑整體較短

補充的審查者 → 作者關係

經欄位可辨識、非自我指向等篩選後，保留 2,058 筆有向審查事件，共 675 種不同的「審查者、PR 作者」有序配對，涉及 108 個審查者帳號與 339 個作者帳號。兩個帳號集合可能重疊，所以 108＋339 不能直接當成不同人數。

同一對帳號可重複出現，因此 2,058 是事件列數、675 是不同配對數。箭頭表示審查對象的方向，並不證明權力、指導或實際影響方向。這裡沒有把全部 5,324 筆 Review 分類事件都當成人際有向邊。

說明結論時必須保留的限制

  1. 觀察邊界有限。只有十個目的性選取的儲存庫、2025 年 1 月、五種公開事件。單一專案帳號可能在未選入的 repo 很活躍。
  2. 公開紀錄不是完整工作。不包含私人或線下活動，也沒有分析每筆修改與對話內容。
  3. 帳號不等於真人。已排除可辨識機器人，但可能仍有自動化、共用或改名帳號；也沒有真人身分認證。
  4. 沒有逐筆核對鏡像。原始快照未保存唯一 event ID，沒有完成逐時原檔比對或依 event ID 的去重。不能保證無重複或遺漏。
  5. 中心度依網絡定義而變。單一專案帳號未進入中心度核心，得到的是跨專案核心的位置。沒有比較多種門檻、月份或權重的敏感度分析。
  6. 結果是描述性的。沒有證明因果、品質、工作量或個人價值，也沒有統計顯著性的主張。

報告可以怎麼收尾？

在這十個專案、這一個月的公開事件中，不同活動的帳號只有部分重疊。大多數帳號只出現在一個選定專案，少數帳號跨越專案，其中一部分同時參與社群類與程式碼類活動。不同中心度提供不同的位置資訊；我們把這些結果當成協作結構的描述，並保留資料與網絡邊界的限制。

下一篇：常見疑問

05｜常見疑問與報告答問

1. 我們到底做了什麼？

我們取得指定範圍的公開活動資料，重新整理與分析。研究重點是「哪些帳號參與哪些專案，以及不同活動的參與帳號有多少重疊」。網站讓大家可以切換活動類型、查看關係，再理解背後的數字。

2. Issue 是真的處理問題？PR 是只提出想法？Review 是點開看過？

這三種理解都需要調整：

名詞 日常比喻 GitHub 上的意思 不能直接推論
Issue（議題） 開一張問題單 記錄問題、需求或待辦；事件也可來自關閉、重新開啟議題 開問題單不等於已修改程式或解決問題
PR（Pull Request） 交出一份修改稿，請負責人收進正式版本 提出分支間的修改供討論與合併；事件也可來自關閉、重新開啟 PR 提出不等於被合併；觸發 PR 事件的帳號不一定是原作者
Review（審查） 審稿並留下意見 對 PR 送出審查或審查留言；本網站合併兩種事件 只是點開、閱讀頁面不算本研究的 Review 事件

例如：小明回報「按鈕失效」是開 Issue；小美寫好修正並送出 PR；小華檢查修改並送出審查。維護者可能合併，也可能要求修改或關閉。這是教學情境，本資料沒有追蹤每個 Issue 是否對應某個 PR。

3. 十個名稱是十份資料集嗎？是同一個人的 GitHub 嗎？

它們是 Hugging Face 組織底下的十個程式碼儲存庫，也就是十個軟體專案。Datasets 恰好是其中一個軟體函式庫的名字。研究用的「資料集」則是這些專案在指定期間的公開事件擷取檔。

不同帳號可以回報問題、留言或送 PR。有寫入權限的成員才能直接寫入主專案；外部貢獻者通常先在自己的分支或 fork 修改，再送 PR。因此不能把所有參與者都當成直接共同編輯主專案的人。

4. 下載後就有 Issue／PR／Review 三欄打勾嗎？

不是。GH Archive 原始檔是壓縮的 JSON 事件紀錄；我們的擷取檔是 JSONL，每行一筆事件，有時間、帳號、專案、事件類型、動作等九個欄位。同一帳號可能有很多行。

分析程式才把這些行整理成集合或表格。例如某帳號本月有一次 Issue 活動、十次 PR 活動，就會同時出現在 Issue 與 PR 的帳號集合。比較重疊時每個帳號在每個集合只算一次。

5. 網絡裡有連線，就是修改過程式嗎？

連線表示帳號在該專案至少留下一筆目前選定類型的事件。在「全部」層，提出議題、留言、PR 動作、審查都能產生連線。只看 Review 層時，只有符合 Review 定義的事件能產生連線。

同一帳號在同一專案有一筆或一百筆事件，二元網絡都只有一條線。事件次數另外計算。

6. 1,379、93、59 到底怎麼判斷？

依序問三個問題：

  1. 在清理後的研究資料裡出現過嗎？有 1,379 個不同帳號名稱。
  2. 在至少兩個選定專案出現過嗎？其中有 93 個。
  3. 這 93 個裡，有同時留下「Issue 或討論」和「PR 或 Review」事件嗎？有 59 個。

例如 A 在兩個專案都只留言，算進 93，但不算進 59。B 在一個專案留言、另一個專案送 PR，兩邊都算。C 只在同一專案留言和送 PR，雖然跨活動類型，仍不算進 93 或 59。這些是虛構例子。

7. Jaccard 是「連擊」或連線數嗎？

Jaccard 是兩個集合重疊的比例。像比較兩堂課的選課名單：同時選兩堂的人數，除以至少選一堂的不同人數。

本研究 Issue 與 PR 的 Jaccard 是 125 ÷ 801 ≈ 0.156。它不是連線數，也不記錄動作順序，因此不能說是「先提 Issue、接著送 PR 的連擊」。同一帳號的兩種活動甚至可以發生在不同專案、不同議題。

8. 排除 813 筆機器人事件就是資料清理嗎？

是。先訂規則，再移除不符合研究分析對象的紀錄。813 是事件列數，不是帳號數。規則是帳號名稱以 [bot] 結尾，或名稱為 HuggingFaceDocBuilderDev；不保證抓到全部自動化活動。

9. 沒下載全部逐時壓縮檔，會比較不精確嗎？

下載多少無關事件，和我們的研究範圍是否完整，是兩件需要分別檢查的事。只查詢指定範圍可以很有效率，但仍要確認時間、事件、專案條件以及服務是否截斷資料。

本研究的來源是 GH Archive 的 ClickHouse 鏡像，分四段取得所選紀錄；沒有逐筆核對 GH Archive 原始檔，也沒有擷取原始事件 ID 做去重。因此應說「依鏡像回傳的研究範圍分析」，不能保證與原檔完全一致。細節與可改進之處見重現步驟。

10. Eigenvector 最高就是最厲害的人嗎？

它衡量在指定網絡裡，是否連到同樣較中心的節點。在本研究，帳號連到的是儲存庫；帳號與儲存庫的分數互相影響。最高帳號分數縮放成 1，並不代表百分之百的能力或影響力。

Degree 看參與幾個專案，closeness 看到其他節點的距離，betweenness 看最短路徑的中介位置，eigenvector 看與高分節點的連結。四種指標各有問題意識，不能直接合成「誰最有貢獻」的結論。

11. 和課堂資料有什麼相似之處？

課堂 W02 的 Davis 個案是「女性 × 社交活動」：某人參加某活動記 1。本研究是「帳號 × 儲存庫」：某帳號在某專案有指定事件記 1。兩者都是雙模資料，有兩種不同類型的節點。資料結構相似，研究對象與關係意義不同。

12. 其他人需要我的 GPT 或電腦才能看嗎？

公開 GitHub Pages 網站由 GitHub 提供。讀者用瀏覽器開啟網站網址即可，不需要登入 ChatGPT，也不需要你的電腦開機。127.0.0.1 則是每個人自己電腦的本機網址，不適合拿來分享。

可以記住的報告說法

我們分析十個 Hugging Face 專案在 2025 年 1 月的公開事件，用「帳號參與專案」建立雙模網絡。不同活動的帳號部分重疊，1,379 個帳號中有 93 個跨專案，其中 59 個又跨兩類活動。中心度幫助我們描述網絡位置，但不代表個人能力或貢獻價值。

術語依據：GitHub 事件定義、About pull requests、GH Archive。研究數字與條件見計算方法。

專案提供什麼？

  • analysis/events.sql：十個儲存庫 ID、五種事件與時間邊界。

  • guide/ 與 analysis/build_guide.py：導讀原稿與靜態網頁產生程式。

原始 data/raw-events.jsonl 未附在公開儲存庫。只有這個儲存庫時，可以檢查分析程式與已發布結果，也可以重新查詢；若要針對原始擷取檔完全重算，仍須另取得該檔，並比對 SHA-256。雜湊能識別檔案版本，不能證明來源完整或內容正確。

  2. 每段另查符合條件的總列數，和下載列數比較；超過上限就再縮短區間。
  3. 若來源可提供，保留事件 ID 與帳號 ID，以便辨識重複和帳號改名。
  4. 以相同時間、儲存庫和事件定義，比對 GH Archive 原始逐時檔。
  5. 延長觀察期間、擴充樣本，再確認結論是否穩定。

這些是後續改進方向，不是本次已完成的工作。目前分析未進行隨機抽樣、顯著性檢定、因果推論或中心度門檻的敏感度分析。

GitHub Pages 如何發布？

本專案使用靜態網站，不需要資料庫或伺服器程式。

  1. GitHub 儲存庫 → Settings → Pages。
  2. Source 選 Deploy from a branch。
  3. Branch 選 main，資料夾選 /docs，儲存。
  4. 等待 GitHub Pages 部署完成，開啟 公開網站。

之後把更新推送到 main 的 docs/，GitHub Pages 就會重新發布。網站使用相對路徑，因此可在 /sna-j-gharchive/ 這個專案網址下正常讀取樣式與資料。.nojekyll 讓這份現成的 HTML／CSS／JavaScript 以靜態檔發布。
